## 0. 一句话需求

为 pioneer-mcp 的**持久化串口监视器**做一个 **MCP Apps 内嵌 UI 面板**：
让用户在支持 MCP UI 的宿主（如 Claude、其他 MCP 客户端）里，
以实时滚动日志的形式查看 `pio device monitor` 的输出，而不是让 AI 把一行行日志读进对话里再复述。

---

## 1. 背景：pioneer-mcp 是什么，这个面板为什么值得做

### 1.1 项目定位
pioneer-mcp 是一个**与具体开发板无关**的 Model Context Protocol (MCP) 服务器，
把 PlatformIO Core CLI 封装成一套**结构化执行层**，供 AI Agent 调用来做嵌入式开发
（编译、上传、串口监视、板卡查询、工程初始化等）。目标硬件：ESP32、AVR Arduino、STM32/RP2040。

当前已实现 14 个工具（v0.1.0 已发 GitHub Release），其中与本简报直接相关的是**持久化串口监视器**三件套：
`open_monitor_session` / `read_monitor_session` / `close_monitor_session`。

### 1.2 为什么串口监视器需要「持久化会话」（务必理解这个前提）
打开串口会触发 DTR/RTS 电平变化，**这会复位大多数开发板**。
因此「一次性抓取」只能看到开机 banner，之后的输出全部丢失。

pioneer-mcp 的做法：**打开一次，保持一个 `pio device monitor` 进程常驻**，
之后多次 `read` 只是从缓冲区增量取行，**不重新复位板子**。这正是「MCP over CLI」相对裸 CLI 的核心优势。

### 1.3 为什么要做内嵌 UI（这个面板的价值）
现状：AI 每次 `read_monitor_session` 拿到一批行，再用文字转述给用户 —— 又慢、又丢细节、还挤占对话上下文。
串口日志本质是**高频、连续、时间序列**的流，天然适合一个**独立的实时滚动面板**来呈现：
用户直接盯着日志滚动，AI 只在需要时介入分析。这就是本面板要解决的体验问题。

## 2. 什么是 MCP Apps 内嵌 UI（接手方需要先核对的规范）

MCP Apps（内嵌 UI / `ui://` 资源，社区中也称 MCP-UI，相关提案见 SEP / MCP-UI 生态）
允许 MCP 服务器返回一个**可在宿主内渲染的 UI 资源**（通常是一段沙箱化的 HTML / iframe），
UI 通过 `postMessage` 桥接与宿主通信，进而**回调 MCP 工具**、订阅数据、渲染结果。

> ⚠️ **给接手方的第一条行动项**：MCP Apps/UI 规范仍在演进，不同宿主（Claude、
> 各类 MCP 客户端）支持程度不一。**请先核实目标宿主当前实际支持的 UI 资源形态与桥接 API**
> （资源 MIME 类型、iframe 沙箱策略、UI→工具调用的消息协议、是否支持服务端主动推送 vs 只能 UI 轮询）。
> 本简报的交互设计以「**UI 只能通过调用工具来拉取数据（轮询）**」为**保守基线**，
> 若目标宿主支持服务端推送/订阅，可在此基础上升级为推流。

接手方需要在方案里明确回答：
- UI 资源怎么声明与返回？（新增一个 `ui://…` 资源，还是让某个工具返回 UI 资源？）
- UI 侧如何触发 `read_monitor_session`？（宿主提供的 tool-call 桥接）
- 渲染载体是完整 HTML + JS 的 iframe，还是受限模板？沙箱能否跑定时器/`fetch`？

## 3. 真实数据契约（全篇地基 —— 不要臆造字段）

以下全部来自现有源码 `src/tools/monitor-session.ts` 与 `src/pio/monitor.ts`，是**面板唯一能依赖的真实数据**。
UI 设计必须严格贴合这些字段与语义；**任何界面上出现的数据点都必须能从这里推导出来**。

### 3.1 会话生命周期（三个工具）

#### `open_monitor_session` — 打开会话
输入：
```
{
  port: string        // 必填，串口号，如 "COM5" / "/dev/ttyUSB0"，由 list_devices 发现
  baud?: number       // 可选正整数；省略时用 platformio.ini 的 monitor_speed
}
```
成功返回 `data`：
```
{
  sessionId: string   // 后续 read/close 的句柄
  port: string
  baud?: number
  meta: { operationType: "monitor", executionStatus: "succeeded" }
}
```
附带 `warnings`（UI 应展示）：`"Opening the port typically resets the board; the first reads may include boot output."`
附带 `nextActions`：提示调用 read / close。

#### `read_monitor_session` — 读取输出（增量 / 全量）
输入：
```
{
  sessionId: string
  fromStart?: boolean   // 默认 false=只取「上次读取之后的新行」；true=返回整个保留缓冲区
}
```
成功返回 `data`：
```
{
  sessionId: string
  status: "running" | "exited"   // 监视进程是否还活着
  exitCode?: number | null       // exited 时的退出码（可能 unknown/null）
  lines: string[]                // 本次取到的行（已按 \r?\n 切分，不含换行符）
  droppedLines: number           // 见 3.2，缓冲溢出导致「本次读取游标之前」丢失的行数
  meta: { operationType: "monitor", executionStatus: "succeeded" }
}
```
`status`：顶层响应状态；当 `droppedLines>0` 或进程已 `exited` 时为 `"warning"`，否则 `"ok"`。
可能的 `warnings`：
- `"{n} line(s) were dropped from the buffer before this read; poll more frequently to avoid loss."`
- `"Monitor process has exited (code {code}); no further output will arrive."`
未找到会话时返回 error：`"No monitor session found with id {id}."`

#### `close_monitor_session` — 关闭会话、释放串口
输入：`{ sessionId: string }`
成功返回 `data`：
```
{
  sessionId: string
  port?: string
  totalLines?: number   // 本会话有史以来产生的总行数（含已被丢弃的）
  meta: { operationType: "monitor", executionStatus: "succeeded" }
}
```

### 3.2 缓冲与丢行机制（面板必须如实呈现，这是诚实性底线）

底层 `src/pio/monitor.ts` 的关键实现细节：

- **环形缓冲**：每个会话最多保留 `MONITOR_BUFFER_LINES = 2000` 行；超出时从头丢弃最旧的行。
- **按行切分**：进程 stdout/stderr 的 chunk 按 `\r?\n` 切分；**未以换行结尾的尾部残段（`pending`）暂不作为完整行返回**，等后续 chunk 补齐。→ UI 不会看到「半行」，但也意味着最后一行若无换行会延迟出现。
- **单调计数**：
  - `totalProduced`：有史以来产生的总行数（即使被环形缓冲丢弃仍累加）。
  - `readCursor`：调用方下一条「尚未读取」的行的单调索引。
- **增量读取语义**（`fromStart=false`，默认）：
  - `bufferStart = totalProduced - lines.length`（当前缓冲区里最旧一行的全局索引）。
  - 若 `readCursor < bufferStart`，说明**游标指向的行已被环形缓冲挤掉** → 这部分记为 `droppedLines`，无法找回。
  - 读取后 `readCursor` 前移到 `totalProduced`（读到最新）。
- **全量读取语义**（`fromStart=true`）：返回当前保留的整段缓冲（≤2000 行），`droppedLines` 恒为 0，并把游标同步到最新（后续增量读接续）。

> **对 UI 的硬性含义**：
> 1. 面板不能假装「日志完整无缺」。当 `droppedLines>0`，界面必须显式插入一条「⚠ 丢失 N 行（轮询太慢）」的占位/断层标记，而不是静默拼接。
> 2. 2000 行是硬上限，历史区不是无限回溯。面板可自行在**前端**保留更长历史（把每次 read 的行累积到本地），但要清楚这只是前端缓存，跨会话/刷新即失。
> 3. `hasMore` 字段目前底层恒为 false（未做分页背压），UI 不要依赖它做「还有更多」判断；判断「是否读到最新」应以「本次 lines 为空且 status=running」为准。

## 4. 面板交互设计（需求，非实现）

### 4.1 核心心智
面板 = **一个实时滚动的串口日志终端**，绑定到**一个** `sessionId`。
它是「AI 帮我打开了监视会话」之后，用户用来**直接盯日志**的可视化窗口。

### 4.2 状态机（面板自身的 UI 状态，独立于会话状态）
1. **未绑定**：还没有 sessionId（例如面板刚渲染、或用户尚未选择会话）。给出引导：让 AI 调 `open_monitor_session`，或从已知会话里选一个。
2. **运行中（running）**：定时增量轮询 `read_monitor_session`，新行追加滚动。这是主状态。
3. **已退出（exited）**：进程结束。停止轮询，顶部横幅显示退出码，日志冻结但可回看。
4. **错误/失联**：read 返回 "No monitor session found" → 视为会话已被关闭/失效，切到终态并提示重开。

### 4.3 必备界面元素（都能由 §3 数据支撑）
- **顶部状态栏**：port、baud（若有）、`status` 徽标（running=绿/exited=灰）、退出码（exited 时）、`totalLines` 累计计数。
- **日志主区**：等宽字体、逐行滚动、自动贴底（autoscroll）。用户上滚时暂停自动贴底，出现「跳到底部」悬浮按钮。
- **丢行断层标记**：当某次 read 的 `droppedLines>0`，在对应位置插入醒目的「⎯⎯ 丢失 N 行 ⎯⎯」分隔条（§3.2 硬性要求）。
- **控制条**：
  - 开始/暂停轮询（暂停≠关闭会话，只是前端停止拉取）。
  - 轮询频率（见 4.4）。
  - 清屏（只清前端显示，不影响后端缓冲/游标）。
  - 「从头加载」按钮 → 触发一次 `fromStart=true` 读取（拉回最多 2000 行保留缓冲）。
  - 关闭会话按钮 → `close_monitor_session`（**破坏性**：释放串口，需二次确认）。
- **前端搜索/过滤**（可选增强）：对已累积的前端行做关键字高亮/过滤（不回调后端）。
- **warnings 展示**：把工具返回的 warnings（丢行、进程退出、开机复位提示）以非阻塞条幅呈现。

### 4.4 轮询节奏（保守基线，因为可能只能 UI 主动拉）
- 默认间隔建议 **500ms–1s**；提供档位（如 250ms / 500ms / 1s / 2s）。
- 轮询太慢 + 板子高频打印 → 触发 `droppedLines`（2000 行环形缓冲被冲掉）。UI 应在检测到持续丢行时**提示用户调快频率**（复用后端 warning 文案）。
- 若目标宿主支持**服务端推送/订阅**，接手方应优先设计为推流，把轮询作为降级方案。**这是需要接手方核实规范后决策的关键分叉点。**

### 4.5 边界与错误呈现
- open 的复位 warning：首次进入运行态时以提示条显示「开串口通常会复位板子，前几行可能是启动输出」。
- exited：横幅「监视进程已退出（code X），不会再有新输出」，停止轮询。
- 会话找不到：终态卡片「会话已失效」，引导重新 open。
- 半行延迟（§3.2 pending）：正常现象，无需特殊 UI，但接手方需知晓「最后一行可能延迟到下次 read 才出现」。

## 5. 无硬件开发路径（关键：用户当前没有任何硬件）

**约束**：本项目负责人手头**没有开发板、没有串口设备**，无法产生真实串口输出。
因此面板**必须能在纯 mock 数据下完整开发、演示、评审**，不得把「插着板子」当作开发前提。

底层已经为此留好了注入点（无需真机即可跑）：
- `src/pio/monitor.ts` 导出 `setMonitorSpawner(next?)`：可注入一个**假的监视进程**，
  它按 `MonitorProcess` 接口（`onData(listener)` / `onExit(listener)` / `kill()` / `pid`）
  **定时吐出伪造的串口文本行**，走的是和真机**完全相同**的缓冲/切分/游标/丢行代码路径。
- 这意味着：mock spawner + 真实的 `open/read/close` 逻辑 = 面板能拿到**结构完全真实、只是内容伪造**的数据流。

给接手方的 mock 方案要求：
1. 提供一个可调的**假串口数据源**：可控行频率（用于演示正常流）、可切到「爆发式高频」（用于**故意触发 `droppedLines`**，验证丢行断层 UI）、可注入多行 boot banner（验证开机输出提示）、可主动触发 `exited`（验证退出态）。
2. 面板的前端开发不应直连真机；应能对着 mock 会话把 §4 的所有状态（running / exited / 丢行 / 找不到会话）**全部走一遍**。
3. 评审交付物应包含「无硬件也能点」的可运行 demo（哪怕是前端本地 stub 掉工具调用）。

## 6. 技术约束与非目标

### 6.1 约束
- **数据源唯一**：面板只能消费 §3 三个工具的输出，不得假设存在别的字段/端点（如「订阅」「历史查询」目前都没有）。若需要新增后端能力（如服务端推送、分页游标暴露给 UI），必须作为**明确的后端改动项**列出，由本项目这边评估后再实现。
- **诚实性**：README/Release 一贯坚持「仅 CLI 层验证、无真机验证」。面板同理——凡是 mock 演示，界面/文档都要标注「示例数据」，不得暗示已在真实硬件上验证。
- **沙箱**：UI 在宿主 iframe 沙箱内运行，能力受限（定时器、消息桥、可能无外网）。接手方须按目标宿主实际沙箱能力设计。
- **纯前端、无重依赖**：倾向于原生 HTML/CSS/JS 或极轻量方案，便于塞进单个 UI 资源；避免大型框架/构建链（除非接手方论证必要）。
- **单会话优先**：v0.2 先做「一个面板绑一个会话」。多会话切换/多面板可作为后续增强，不在首版必须项。

### 6.2 明确的非目标（v0.2 不做）
- 不做串口**写入/发送**（当前工具只读监视，无发送通道）。
- 不做跨会话持久化历史存储。
- 不做真机自动发现的 UI（`list_devices` 是另一个工具，可后续接入）。
- 不实现库管理、其它工具的 UI。
